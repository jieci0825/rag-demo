# rag 相关名词

## 指标

### 召回率和精确率
- **召回率（Recall）**：指的是所有相关内容中被检索出来的比例。公式为：

  ```
  召回率 = 检索到的相关内容数量 / 所有实际相关内容的总数
  ```

  例如：实际相关文档有 10 个，系统只检索到其中的 6 个，那么召回率 = 6/10 = 60%

- **精确率（Precision）**：指的是检索出来的所有内容中，真正相关的占比。公式为：

  ```
  精确率 = 检索到的相关内容数量 / 检索到的所有内容数量
  ```

  例如：实际相关文档有 10 个，系统一共返回 8 个，其中 6 个是相关的，那么召回率 = 6/8 = 75%

  也就是说，召回率反映的是系统的**覆盖能力**，而精确率衡量的是系统的**准确性** 。

## chunk

### chunk 切割
> 顾名思义，就是将文档做切块的时候，具体怎么去切

#### Semantic Chunking
按照语义边界来切分文档，而非按照固定的字符数或 token 切割。

**核心目标**：让每个 chunk 尽量保持语义完整，避免一句话出现突兀的拆开或者一段完整的说明被截断。

常见做法如下：
- 按句切分
- 按段落切分
- 按标题层级切分
- 按语义相似度变化点切

#### Recursive Chunking
指的是递归式切分策略，并不是直接按照固定长度硬切，而是根据设定的一组优先级去切分，例如：
1. 先按标题或者段落切分
2. 如果某段还是太长，则按照句子切分
3. 若一句话太长，则按照标点切分
4. 若最后还是过长，则按照字符或 token 长度切分

本质上是“尽量保证语义结构，同时满足长度约束”的折中策略

### chunk 增强
> 指的就是目前 chunk 已经存在，怎样让它更适合检索

#### Contextual Headers
这个方案的实现就是给每一段 chunk 增加一些元数据，比如给这段 chunk 增加上下文信息（标题、章节、段落），这样可以保证这段 chunk 脱离原文，也可以保持必要的信息。因为 chunk 切分完成之后，一个 chunk 只看它本身，是不太好分辨它的含义的。

所以通常会给一段 chunk 添加标题、章节标题、小节标题、所属模块名称...等这样的**上下文头信息**
```json
{
    "metadata":{
        "title": "《支付系统文档》",
        "chapterTitle": "3. 退款流程",
        "sectionTitle": "3.2 审核规则"
    },
    "chunk": "...",
    "content": "审核通过后，将在 24 小时内到账"
}
```
如果单看这句话，其实并不知道这个到账的钱款是退款。

#### Document Augmentation
指的是在索引前对原始文档做增强，补充额外信息，让后续检索效果更好。这种增强不一定改变原文主体内容，但会让文档更适合被切分、检索和理解。

增强的方式很多，例如：
- 给文档补标题
- 给段落补摘要
- 给FAQ补标准问法
- 给知识点补关键词
- 给表格转自然语言描述

我们看一个例子，假设原文为：
```
react hooks 是一种...
```

增强后的：
```
- summary: "介绍 hooks 概念"
- keywords: ["react", "hooks", "useState"]
- QA: "什么是 hooks？"

react hooks 是一种...
```

#### 元数据抽取
指的是在索引阶段，从文档中提取结构化信息，放进 metadata，方便后续检索、过滤、排序和展示。这些 metadata 往往不是正文主体，但对系统很重要。

常见 metadata 包括：
- 文档标题
- 来源路径
- 作者
- 更新时间
- 所属知识库
- 标签
- 权限级别
- 章节标题

例如这句话：
```
所有正式员工每年享有 10 天带薪年假。
```

可以抽取的 metadata 有：
```json
{
    "title": "年假制度",
    "department": "HR",
    "audience": "正式员工",
    "category": "假期政策",
}
```

有了这些元数据之后，就可以实现如下效果：
- 只检索HR文档
- 只检索正式员工适用内容
- 检索后在界面展示来源标题

## 索引构建与治理

### 索引基础

要明白这个概念，就得先明确什么是索引，索引就是由 chunk + embedding + metadata 组成，一个索引若使用伪代码表示的话，则大概如下：

```ts
type IndexItem = {
    id: string
    content: string // chunk 原文
    embedding: number[] // chunk 原文转化后的向量
    metadata: {
        source: string
        title?: string
        tags?: string[]
    }
}
```

### 去重与清洗
指的是在做索引之前，先把重复、噪音、脏数据处理掉，避免它们进入向量库。如果原始数据质量差，后面的 embedding 和检索再好，也很难得到理想效果。

常见操作包括：
- 去除重复文档
- 去除重复chunk
- 去掉空白内容
- 去掉模板页眉页脚
- 去掉乱码和无意义字符
- 标准化格式

### Hierarchical Indexing
指的是按层级结构来建立索引，而不是把所有 chunk 都平铺地放在同一层做检索。

它的核心思想是：**文档本身通常有天然的层次结构**，例如“文档 -> 章节 -> 小节 -> 段落 -> chunk”，如果索引时能保留这种结构，那么检索时就能先粗找，再细找。

这样做的好处是：
- 先在高层级定位主题范围
- 再在低层级找到具体内容
- 降低无关 chunk 被召回的概率
- 提高长文档场景下的检索效率和准确性

举个例子，一篇技术文档可以拆成下面这样的结构：

```text
《支付系统文档》
  ├── 退款流程
  │     ├── 审核规则
  │     └── 到账时效
  └── 支付流程
        ├── 下单
        └── 回调
```

如果用户问的是：
```
退款多久能到账？
```

系统可以先命中“退款流程”这一层，再继续往下找到“到账时效”相关的 chunk，而不是直接在所有 chunk 里无差别搜索。

常见做法包括：
- 给每个 chunk 记录父级节点信息
- 同时建立章节级索引和 chunk 级索引
- 检索时先召回父节点，再展开子节点
- 或者先检索细粒度 chunk，再回溯它的上级结构补充上下文

本质上，它是一种**利用文档结构来优化检索过程**的索引方式，特别适合长文档、手册、制度文档、技术文档这类层级很清晰的内容。

### 增量更新
指的是当原始文档发生变化时，只更新受影响的那一部分索引，而不是把整个知识库重新切分、重新 embedding、重新入库一遍。

它的核心目标是：**降低索引维护成本，同时让知识库内容尽快保持最新**。

如果每次文档有一点点变化，都全量重建索引，那么在数据量大、文档更新频繁的场景下，成本会很高，速度也会很慢。所以更常见的做法是，只处理新增、修改、删除的内容。

常见场景包括：
- 新增了一篇文档
- 某个章节被修改了
- 某些 chunk 内容发生了变化
- 某篇旧文档被删除了

例如原来文档里有一句话：
```
退款将在 3 个工作日内到账。
```

后来更新成：
```
退款将在 1 个工作日内到账。
```

那么系统理想的做法不是重建整篇《支付系统文档》的所有索引，而是：
- 找到受影响的 chunk
- 重新生成这个 chunk 的 embedding
- 更新对应的 metadata
- 替换向量库中的旧记录

如果文档被删除，则通常还需要把对应的 chunk 和向量记录一并删除，避免检索出过期内容。

常见实现方式包括：
- 根据文档 ID 做覆盖更新
- 根据 chunk ID 做局部替换
- 通过内容 hash 判断是否发生变化
- 记录更新时间，只处理最近变更的数据

本质上，增量更新解决的是**索引如何持续维护**的问题。它不是提升单次检索效果的技巧，而是保证知识库在长期运行过程中，既新鲜又可控的重要机制。

## 检索前

> 检索前主要就是针对用户的 query 进行一系列操作

### Query Transformation

Query Transformation 是一个比较大的概念，指的是在真正检索之前，对用户原始 query 做处理，让它更适合检索。

它不是一种具体方法，而是一类方法的统称。例如 query rewrite、query expand、multi-query、query decomposition、HyDE 都可以算作 query transformation。

比如用户问：

这个报错怎么解决？

如果直接拿这句话去检索，效果可能不好，因为“这个报错”缺少上下文。

系统可能会根据当前对话上下文，把它转换成：

React 项目启动时报 Cannot find module 应该怎么解决？

也可能会进一步扩展关键词、生成多种问法，或者拆成多个子问题。

核心是：**用户原始问题不一定适合直接拿去查，所以需要先把 query 变成更适合检索的形式**。

### Query Rewrite

Query Rewrite 指的是对用户原始问题做改写，让它表达得更清楚、更完整、更适合检索，但问题本身并没有变。

比如用户问：

怎么优化这个？

如果结合上下文，系统知道用户说的是“向量检索召回效果不好”，那么可以改写成：

如何优化 RAG 系统中的向量检索召回效果？

这里不是增加多个角度，也不是拆成多个子任务，而是把一个表达不完整、不够清楚的问题，改写成一个更明确的问题。

常见改写方向包括：
- 补全省略的上下文
- 去掉口语化表达
- 统一术语
- 把模糊指代改成明确对象

它的核心目标是：**让 query 更像知识库里可能出现的表达方式**。

### Query Expand

Query Expand 指的是在不改变用户原始意图的前提下，给 query 补充相关词、同义词、近义词或者领域术语，从而提高召回率。

例如用户问：

如何提升检索效果？

系统可以扩展成：

如何提升检索效果 召回率 精确率 rerank query rewrite embedding 相似度

这里用户还是在问“如何提升检索效果”，只是系统额外补充了一些可能出现在文档里的相关表达。

常见扩展内容包括：
- 同义词
- 近义词
- 英文术语
- 缩写
- 领域关键词

它和 query rewrite 的区别在于，query rewrite 更像是**把问题改清楚**，而 query expand 更像是**在原问题上补充更多可检索的词**。

### Multi-query

Multi-query 也是一种 Query 扩展策略。核心是：从不同角度生成多条query,分别检索，再合并结果。
例如，用户问：

如何提高团队研发效率

系统生成多条query:
- 提高研发团队效率的方法
- 软件团队协作效率提升实践
- 研发流程优化OKR sprint code review
- 影响研发效率的常见瓶颈

这里不是简单“加词”，而是生成了多种问法/多种角度。

### Query Decomposition

Query Decomposition 可以看作是一种Query结构化的工作。可以通俗理解成：把一个太大、太复杂、没法直接查的问题，拆成几个更小、更具体、更容易检索的问题。

比如用户提问：A 公司和 B 公司哪家更值得去？

这个问题就比较难去检索，因为“更值得去”的表达过于笼统了。

系统就会先把它拆成几个子问题：
- A公司薪资水平怎么样
- B公司薪资水平怎么样
- A公司加班情况怎么样
- B公司加班情况怎么样
- A公司发展前景怎么样
- B公司发展前景怎么样

它和 multi-query 的区别在于，multi-query 本质是**将一个问题多生成几种问法，但是还是在问一个问题**，而 query-decomposition 本质则是**在查不同的子任务**

### HyDE

HyDE 全称是 Hypothetical Document Embeddings，可以理解成：先让大模型根据用户问题生成一段“假设性的答案文档”，再用这段文档去做 embedding 和检索。

比如用户问：

RAG 为什么会检索不到正确内容？

系统不是直接拿这个问题去向量检索，而是先生成一段可能的回答：

RAG 检索不到正确内容，常见原因包括 query 表达不清晰、chunk 切分不合理、embedding 模型不适配、召回数量过少、rerank 效果不好等。

然后再用这段“假设性文档”去检索。

这样做的原因是：有时候问题本身很短，包含的信息很少，直接 embedding 后不容易命中文档；而一段假设性回答会包含更多相关概念，更接近知识库里的正文表达。

需要注意的是，HyDE 生成的这段内容不是最终答案，也不代表它一定正确。它的作用只是帮助系统更好地检索。

核心是：**先生成一段可能相关的文档，再用这段文档去找真正的资料**。

## 检索操作

### Keyword Search

Keyword Search 也叫关键词检索，指的是根据用户 query 里的关键词，去文档中查找包含这些词的内容。

它更关注的是“词有没有匹配上”，而不是两句话语义上是不是相近。

比如用户问：

退款多久到账？

系统可能会重点去匹配这些词：
- 退款
- 到账
- 多久

如果某个 chunk 里出现了“退款将在 3 个工作日内到账”，那它就很容易被关键词检索命中。

这种方式的优点是很直接，也比较可控。尤其是当用户的问题里包含明确的术语、编号、错误码、函数名、产品名时，关键词检索通常效果很好。

例如：
- ERR_CONNECTION_REFUSED
- useEffect
- 订单号
- 退款规则
- API Key

在真实的 RAG 系统中，Keyword Search 通常不会从零实现，而是直接使用成熟的全文检索引擎。

常见选择包括：
- Elasticsearch
- OpenSearch
- Meilisearch
- Typesense
- 数据库全文索引，例如 MySQL Full-Text Search、PostgreSQL FTS

这些系统内部通常会基于倒排索引来构建高效的关键词检索能力。

倒排索引可以简单理解成：先记录每个词出现在哪些文档里。这样查询某个关键词时，系统不用一篇篇扫描所有文档，而是可以直接找到包含这个词的文档列表。

例如：

```text
退款 -> 文档1、文档3、文档8
到账 -> 文档1、文档5
```

当用户搜索“退款到账”时，系统就可以快速找到同时或部分包含这些词的文档。

倒排索引通常是在写入文档或 chunk 的时候构建的，而不是用户每次提问时临时生成。

放到 RAG 流程里，大概是：

```text
原始文档
-> 清洗
-> chunk 切分
-> 写入全文检索引擎
-> 构建倒排索引
-> 用户 query 来了之后直接检索
```

如果是正常的正排结构，更像是：

```text
文档1 -> 退款、3个工作日、到账
文档2 -> 订单、支付、订单号
文档3 -> 退款、失败、客服
```

正排适合从“文档”找到“这个文档里有哪些词”。但搜索时通常是反过来的：用户给出一个词，系统要找“哪些文档包含这个词”。

所以倒排结构会变成：

```text
退款 -> 文档1、文档3
到账 -> 文档1
订单 -> 文档2
支付 -> 文档2
失败 -> 文档3
```

这样用户搜索“退款到账”时，系统不用扫描所有文档，而是直接查：

```text
退款 -> 文档1、文档3
到账 -> 文档1
```

然后就能知道文档1同时包含“退款”和“到账”，文档3只包含“退款”，因此文档1更可能排在前面。

所以可以简单理解成：

```text
正排索引：文档 -> 词
倒排索引：词 -> 文档
```

对搜索来说，倒排索引更适合，因为搜索的入口就是“词”。

不过，倒排索引里的这些词不是凭空来的。全文检索系统在构建索引时，通常会先通过 Analyzer 对文本做处理。

这个过程大概是：

```text
原文
-> 分词
-> 去标点
-> 大小写归一
-> 停用词过滤
-> 同义词处理
-> 写入倒排索引
```

比如：

```text
退款将在 3 个工作日内到账
```

经过 Analyzer 处理后，可能得到：

```text
退款
3
工作日
到账
```

然后倒排索引记录：

```text
退款 -> 文档1
工作日 -> 文档1
到账 -> 文档1
```

这里需要注意，倒排索引不是由 BM25 来决定哪些词要不要进入索引。哪些词进入索引，主要由 Analyzer 决定，例如分词器、停用词表、同义词规则等。

BM25 的作用是在查询时对命中的文档打分和排序。它会综合考虑关键词是否出现、出现次数、文档长度、这个词在整个文档库里常不常见等因素，尽量把更相关的内容排在前面。

也就是说：

```text
Analyzer 负责：把文本拆成哪些词，并决定哪些词进入倒排索引
倒排索引负责：记录每个词出现在哪些文档里
BM25 负责：在查询时给命中的文档打分排序
```

但它的问题是，如果用户和文档使用了不同的表达方式，就可能检索不到。

比如用户问：

钱什么时候退回来？

而文档里写的是：

退款将在 3 个工作日内到账。

这两个表达语义上很接近，但关键词并没有完全对上，单纯依赖 Keyword Search 就可能漏掉相关内容。

所以在 RAG 中，Keyword Search 经常会和 Vector Search 一起使用。Keyword Search 负责抓住明确词面匹配的内容，Vector Search 负责补充语义相似但关键词不完全一致的内容。

核心是：**Keyword Search 查的是词面匹配，适合明确关键词、术语、编号、错误码这类场景**。

### Vector Search

Vector Search 也叫向量检索，指的是先把 query 和文档都转换成向量，再根据向量之间的相似度来查找相关内容。

它更关注的是“语义是不是接近”，而不是关键词有没有完全匹配上。

比如用户问：

钱什么时候退回来？

文档里写的是：

退款将在 3 个工作日内到账。

如果只看关键词，“钱”“退回来”和“退款”“到账”并没有完全一致。但从语义上看，它们问的是同一类事情。

向量检索要解决的就是这种问题：**用户的表达和文档的表达不一样，但意思接近，也能被检索出来**。

它的大致流程是：

```text
文档 chunk
-> embedding 模型
-> 文档向量
-> 存入向量库

用户 query
-> embedding 模型
-> query 向量
-> 和文档向量计算相似度
-> 返回最相似的 chunk
```

这里的 embedding 模型，可以理解成一个“把文本转换成数字表示”的模型。文本经过 embedding 之后，会变成一组数字，例如：

```text
退款将在 3 个工作日内到账 -> [0.12, -0.08, 0.35, ...]
钱什么时候退回来 -> [0.10, -0.06, 0.32, ...]
```

真实系统里的向量维度通常会很高，可能是几百维，也可能是上千维。我们不需要手动理解每一个数字代表什么，只需要知道：语义越接近的文本，它们的向量在空间里的距离通常越近。

所以向量检索不是在查“有没有某个词”，而是在查“哪段内容和这个问题在语义空间里更接近”。

在真实的 RAG 系统中，Vector Search 通常也不会从零实现，而是使用向量数据库或者带向量检索能力的数据库。

常见选择包括：
- Milvus
- Pinecone
- Weaviate
- Qdrant
- Chroma
- pgvector
- Elasticsearch / OpenSearch 的向量检索能力

这些系统会为向量建立索引，方便快速查找相似向量。

因为真实业务里的 chunk 可能很多，如果每次查询都拿 query 向量和所有文档向量逐个计算相似度，数据量一大就会很慢。

所以向量库通常会使用 ANN，也就是 Approximate Nearest Neighbor，近似最近邻搜索。

它的意思是：不一定每次都暴力找到绝对最相似的向量，而是在速度和准确性之间做一个折中，快速找到足够相似的一批结果。

常见的向量相似度计算方式包括：
- Cosine Similarity
- Dot Product
- Euclidean Distance

可以简单理解成，它们都是在衡量 query 向量和文档向量“离得近不近”。

举个例子：

```text
query：钱什么时候退回来？

chunk1：退款将在 3 个工作日内到账。
chunk2：订单支付成功后会生成订单号。
chunk3：公司年假每年 10 天。
```

向量检索可能会判断：

```text
chunk1 和 query 语义最接近
chunk2 有一点相关
chunk3 基本无关
```

然后优先返回 chunk1。

它的优点是可以处理同义表达、口语化表达、模糊问题，也更适合问答、知识库、客服这类场景。

但它也有局限。

如果用户的问题里包含非常明确的词，例如错误码、订单号、函数名、专有名词，向量检索不一定比关键词检索更稳定。

例如：

```text
ERR_CONNECTION_REFUSED
useEffect
order_123456
```

这些内容的关键点不是语义相似，而是精确匹配。这个时候 Keyword Search 往往更可靠。

所以在 RAG 中，经常会把 Keyword Search 和 Vector Search 结合起来使用，也就是 Hybrid Search。

Keyword Search 负责找词面明确匹配的内容，Vector Search 负责找语义相似的内容。两边分别召回结果之后，再合并、排序，或者交给 rerank 模型重新排序。

核心是：**Vector Search 查的是语义相似，适合用户表达和文档表达不完全一致的场景**。

### Metadata Filtering

Metadata Filtering 也叫元数据过滤。它根据文档上的结构化 metadata 限制哪些记录可以参与检索，本身不计算 query 和文档的相似度。

例如一个 RAG 系统里有多个知识库和大量文档，每个文档可以记录：

```json
{
    "knowledgeBaseId": "company-policy",
    "department": "HR",
    "year": 2026,
    "allowedRoles": ["HR", "管理员"]
}
```

这里需要注意，Metadata Filtering 本身不会判断用户拥有哪些权限。用户身份和权限通常由业务系统判断，业务系统再把判断结果转换成过滤条件，交给检索引擎执行。

例如当前用户的角色是 HR，并且查询“2026 年 HR 部门的年假制度”，整个过程可以是：

```text
业务系统验证用户身份和权限
-> 生成 allowedRoles 包含 HR、department = HR、year = 2026
-> 检索引擎根据 metadata 限定候选文档
-> 在候选文档中执行 Keyword Search 或 Vector Search
```

过滤条件通常来自：
- 系统上下文，例如当前用户、角色、租户和可访问知识库
- 用户明确选择的条件，例如部门、时间和文档类型
- 从 query 中提取的条件，例如从“2026 年的年假制度”中提取 `year = 2026`

多个知识库也不一定都通过 metadata 区分。系统还可以使用不同的 index、collection 或 namespace 做物理或逻辑隔离，metadata 只是其中一种实现方式。

所以可以简单理解成：

```text
业务系统负责：判断用户身份和权限，并生成过滤条件
Metadata Filtering 负责：根据条件限定参与检索的记录
Keyword Search / Vector Search 负责：在限定范围内判断内容相关性
```

核心是：**Metadata Filtering 根据权限结果、知识库、部门、时间等结构化条件缩小检索范围，但不负责权限决策，也不参与 query 与文档的相似度计算**。

### Small-to-Big Retrieval

Small-to-Big Retrieval 可以理解成：**检索时使用较小的 chunk 精确定位相关内容，命中后再取回它所属的较大上下文交给大模型**。

它是 RAG 工程中常用的一种检索模式，但不是定义完全统一的标准算法名称。相关论文更多是在研究检索粒度，以及如何结合细粒度检索和父级上下文。

为什么要这样做？因为 chunk 大小存在一个矛盾：

- 小 chunk 信息集中，更容易和 query 精确匹配，但可能缺少上下文
- 大 chunk 上下文完整，但可能包含较多无关内容，影响检索精度

例如原文有一个完整段落：

```text
退款申请需要先经过审核。审核通过后，退款将在 3 个工作日内到账。
如果审核不通过，系统会通知用户补充材料。
```

系统可以把其中的小句子作为检索单元：

```text
审核通过后，退款将在 3 个工作日内到账。
```

当用户问“退款多久到账”时，先用这个小单元完成精确匹配，再根据它记录的 `parentId`，取回所属的完整段落交给大模型。

整个过程大概是：

```text
原始文档
-> 建立大 chunk
-> 将大 chunk 再拆成小 chunk
-> 小 chunk 记录 parentId 并建立检索索引

用户 query
-> 检索小 chunk
-> 找到对应的大 chunk 或相邻内容
-> 将较完整的上下文交给大模型
```

常见实现方式包括：

- Parent-Child Retrieval：检索子 chunk，返回它所属的父 chunk
- Sentence Window Retrieval：检索命中的句子，再补充前后若干句

论文研究也支持这种设计背后的粒度权衡：

- [Dense X Retrieval](https://arxiv.org/abs/2312.06648) 的实验表明，检索单元的粒度会明显影响检索效果，命题、句子等细粒度单元通常比大段落包含更高密度的相关信息。
- [Rethinking Chunk Size for Long-Document Retrieval](https://arxiv.org/abs/2505.21700) 发现，小 chunk 更适合精确、事实型问题，而需要广泛上下文的问题可能受益于大 chunk。
- [H-RAG](https://arxiv.org/abs/2605.00631) 使用细粒度子节点进行检索，再在生成阶段聚合父级上下文，体现了类似的父子检索思路。

需要注意的是，返回的上下文并不是越大越好。如果父 chunk 或扩展窗口过大，仍然会带入无关内容、增加 token 消耗。因此小 chunk 和大上下文的尺寸需要根据文档结构和问题类型进行评估。

核心是：**用小 chunk 提高检索精度，再用它对应的大上下文补全语义，让“检索准确”和“上下文完整”不必使用同一个粒度**。

### Hypothetical Retrieval

Hypothetical Retrieval 不是定义完全统一的标准算法名。这里主要指 **Hypothetical Questions Retrieval，也就是假设问题检索**。

它的核心是：在索引阶段，让大模型根据每个 chunk 预先生成几个“这段内容可以回答的问题”，并对这些问题建立向量索引。

例如原文是：

```text
审核通过后，退款将在 3 个工作日内到账。
```

系统可以生成：

```text
退款多久到账？
退款审核通过后需要等待几天？
```

用户查询时，系统先匹配这些假设问题，再返回它们对应的原始 chunk。

```text
文档 chunk
-> 生成假设问题
-> 对假设问题建立索引

用户 query
-> 匹配相似的假设问题
-> 返回对应的原始 chunk
```

这样做是为了把传统的“问题与文档匹配”，转换成表达形式更接近的“问题与问题匹配”。

它和 HyDE 的区别是：

```text
Hypothetical Questions Retrieval：索引阶段为文档生成假设问题
HyDE：查询阶段根据用户问题生成假设答案
```

[QuOTE](https://arxiv.org/abs/2502.10976) 和 [HyPE](https://papers.ssrn.com/sol3/papers.cfm?abstract_id=5139335) 都研究了这种利用假设问题改善 query 与文档语义对齐的思路。

需要注意的是，生成问题会增加索引成本。如果假设问题遗漏了用户可能采用的表达方式，仍然可能检索不到，因此通常需要和原始 chunk 检索结合使用。

核心是：**预先为文档生成它可能回答的问题，通过问题与问题的匹配找到对应的原始内容**。
